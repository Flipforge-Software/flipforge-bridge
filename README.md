# Flipforge Bridge

Secure local Wi-Fi transport firmware for the official Flipper Zero Wi-Fi Developer Board.

Flipforge Bridge v0.1.3 carries the existing Flipper protobuf RPC byte stream over an authenticated TCP connection. It is a transport, not a backup engine, RPC replacement, web service, or Flipper application.

```text
Flipforge iOS / test client
       │ WPA2 SoftAP + authenticated TCP :4242
       ▼
Flipforge Bridge (ESP32-S2 Wi-Fi Devboard)
       │ official Expansion Module Protocol over UART
       ▼
Flipper Zero
       │ standard protobuf RPC
       ▼
Flipper services and Flipforge Core.fap
```

> Installing Flipforge Bridge replaces the current Wi-Fi Devboard firmware until stock firmware is reflashed. It does **not** replace or modify Flipper Zero firmware.

## Features

- Official Flipper Expansion Module Protocol framing, checksum, 64-byte DATA limit, status acknowledgement, heartbeat, START RPC, and STOP RPC.
- Deterministic UART recovery with three bounded retries. It never reboots the ESP32 for a recoverable UART fault.
- Direct WPA2 SoftAP named `Flipforge-XXXX`, with a unique random password and pairing secret stored in NVS.
- HMAC-SHA256 client authentication with fresh 32-byte nonces and an 8-byte session ID.
- One active client, bounded buffering, UART backpressure, partial TCP-send handling, and no silent RPC-byte loss.
- DEBUG metrics for TCP, Expansion, RPC payload, acknowledgements, queue use, retries, and errors.
- Non-blocking blue LED activity pulses for actual RPC payload traffic; idle heartbeats and status frames do not cause flicker.
- Entirely local data path. The firmware has no station mode, cloud relay, analytics, or Internet client.
- TinyUSB CDC console that can enumerate when USB is connected after the Devboard has already booted from Flipper power.

## Supported hardware

v0.1 targets only the official Flipper Zero Wi-Fi Developer Board with ESP32-S2.

The mapping is verified from Flipper's Expansion documentation and the official Devboard firmware:

| Signal | ESP32-S2 UART | ESP32-S2 GPIO | Flipper GPIO pin |
|---|---:|---:|---:|
| Devboard TX / Flipper LPUART RX | UART1 | 17 | 16 |
| Devboard RX / Flipper LPUART TX | UART1 | 18 | 15 |

The ESP32-S2 mapping is verified against the official Wi-Fi Devboard firmware's
[`cli-uart.c`](https://github.com/flipperdevices/blackmagic-esp32-s2/blob/dev/main/cli-uart.c),
which routes UART1 through GPIO 17 (TX) and GPIO 18 (RX). This keeps Bridge off
the board's UART0 USB-UART route.

The onboard active-low RGB LED uses the official firmware mapping from
[`led.c`](https://github.com/flipperdevices/blackmagic-esp32-s2/blob/dev/main/led.c):
red GPIO 6, green GPIO 5, and blue GPIO 4. Bridge uses only the blue channel for
transfer activity and keeps the same low visible-duty limit as the stock driver.

Do not use this build on an arbitrary ESP32-S2 board without reviewing its wiring.

## Build

The supported toolchain is ESP-IDF v5.5.5.

```bash
git clone --branch v5.5.5 --recursive https://github.com/espressif/esp-idf.git ~/esp/esp-idf-v5.5.5
cd ~/esp/esp-idf-v5.5.5
./install.sh esp32s2
. ./export.sh

cd ~/Desktop/flipforge-bridge
idf.py set-target esp32s2
idf.py build
```

Run host tests separately:

```bash
make test
```

## Flash

1. Remove the Devboard from the Flipper and connect its USB-C port to the Mac.
2. Hold **BOOT**, press and release **RESET**, then release **BOOT**.
3. Find the new serial port with `ls /dev/cu.*`.
4. From this project with ESP-IDF exported, flash using the bootloader port:

   ```bash
   idf.py -p /dev/cu.YOUR_BOOTLOADER_PORT flash
   ```

5. Press **RESET**, list ports again, and monitor using the runtime port:

   ```bash
   ls /dev/cu.*
   idf.py -p /dev/cu.YOUR_RUNTIME_PORT monitor
   ```

The bootloader and runtime ports may have different names. After RESET, allow up to five seconds for the TinyUSB runtime port to appear. `idf.py` uses the offsets and images generated by this exact build; no offsets are hardcoded here. Exit the monitor with `Ctrl-]`.

For a packaged artifact, enter bootloader mode, `cd` into the extracted artifact, activate ESP-IDF v5.5.5, and run `python -m esptool --chip esp32s2 -p /dev/cu.YOUR_DEVBOARD write_flash @flash_args`. The packaged paths match the generated argument file.

## Flipper Expansion configuration

On the Flipper, open **Settings → Expansion Modules** and enable **Listen UART** for **LPUART**. Attach the Devboard only after flashing and rebooting it. The module waits three seconds for Flipper startup, initiates detection at 9600 baud, negotiates a supported baud, and maintains the link with heartbeats below the official 250 ms timeout.

## Pairing

The first boot creates a 120-second physical pairing window. A later window can be opened by holding the Devboard **BOOT** button for two seconds.

Pairing is deliberately available only through the physical USB console in v0.1:

1. Connect the Devboard USB-C port to a trusted Mac while Bridge is running.
2. Open its serial console at 115200 baud.
3. Hold **BOOT**, type `PAIR`, and press Return before the 120-second window expires.
4. The console returns one line:

   ```text
   FFPAIR1 <ssid> <wpa2-password> <64-character-pairing-secret-hex>
   ```

This line contains secrets. Store the pairing secret in the iOS Keychain and do not paste it into logs, issues, or screenshots. Bridge never emits it through ESP-IDF logging. The pairing window then closes.

## iOS transport contract

The management framing, HMAC input, and raw-mode transition are defined in [docs/PROTOCOL.md](docs/PROTOCOL.md). An iOS `BridgeRPCTransport` should implement only the byte transport and reuse the existing `FlipperRPCClient` protobuf implementation.

Normal RPC operations—including properties, `/ext` storage, app launch, App DataExchange, and Flipforge Core capabilities—remain Flipper RPC operations. Bridge does not interpret or duplicate them.

## Security

- WPA2 SoftAP with a per-device 20-character random password.
- Independent 256-bit random pairing secret persisted in NVS.
- HMAC-SHA256 challenge response with fresh nonces for replay resistance.
- Constant-time HMAC comparison, strict length checks, one active client, bounded queues, and timeouts.
- No RPC proxy is opened before authentication.
- No secret, raw RPC payload, filename, NFC/RFID content, or user data is logged.

Physical access to the USB console and BOOT button is trusted during pairing. Erasing NVS resets both credentials.

## Diagnostics

The onboard LED briefly pulses blue after successful RPC payload transfers in
either direction. Continuous traffic appears as a controlled stutter rather
than a solid light. This work runs in a low-priority task and never waits in the
UART or TCP transfer path. Disable it with `idf.py menuconfig` under
**Flipforge Bridge → Flash onboard RGB LED for RPC data** if needed.

When `CONFIG_FLIPFORGE_DEBUG_METRICS` is enabled, Bridge logs a snapshot every five seconds with actual counters only: TCP/Expansion bytes, RPC bytes per second, frame count, mean ACK wait, queue peak, retries, errors, and negotiated baud. Production defaults disable these counters; enable them through `idf.py menuconfig` for a measured hardware run.

The test client can authenticate, inspect status, and send a caller-supplied valid protobuf RPC stream:

```bash
read -s FLIPFORGE_PAIRING_SECRET
export FLIPFORGE_PAIRING_SECRET
python3 tools/bridge_client.py --host 192.168.4.1 status

python3 tools/bridge_client.py \
  --host 192.168.4.1 \
  rpc --input request.bin --output response.bin \
  --expected-response-bytes 128 --response-seconds 5
```

The tool reports measured bytes, duration, and effective KiB/s. Give the exact expected response size for a bounded measurement; otherwise the configured response wait is included. It never generates fake RPC traffic.

## Limitations

- Official ESP32-S2 Wi-Fi Devboard only.
- SoftAP only; no home-network mode or Bonjour.
- One active client.
- USB-console physical pairing is intentionally basic.
- No OTA updates, web dashboard, cloud relay, backup protocol, or direct Internet access.
- `EndRPCProxy` is achieved by closing the raw TCP session. Management frames cannot be injected into the raw protobuf stream.
- Hardware behavior and throughput still require the manual tests in [docs/HARDWARE_TEST_PLAN.md](docs/HARDWARE_TEST_PLAN.md).

## Restore stock Devboard firmware

Flipper officially supports stock Devboard recovery with uFBT:

1. Install uFBT: `pipx install ufbt`.
2. Connect the Devboard to USB-C.
3. Hold **BOOT**, press and release **RESET**, then release **BOOT**.
4. Run `python3 -m ufbt devboard_flash`.
5. Press **RESET** after `WiFi board flashed successfully`.

This restores official Devboard firmware and does not alter the Flipper Zero firmware.
